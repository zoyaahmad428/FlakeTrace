01

What a POC had to prove

The evaluation guide is explicit that reproducing a flaky test proves nothing — that order-dependent failures can be rerun is already established. The POC therefore had to test the project's incremental claim:

The tested hypothesis

Can a bounded static-field overlap signal prioritise true OD-relevant tests and reduce confirmation executions, measured against original-order one-by-one (OBO) and random baselines on real, buildable cases?

Two consequences follow. First, a fair baseline is mandatory — a result is only meaningful relative to OBO and random. Second, the cost unit must be test-method invocations, not Maven launches, because one Maven launch can execute wildly different numbers of tests.

All definitions were frozen and committed before any experiment ran, so the analysis could not be tuned to flatter the outcome.

$ git log --oneline

02

Environment and provenance

Every execution ran inside a pinned container so results do not depend on the host machine. The Maven cache is a named Docker volume, keeping dependency resolution reproducible and separate from test execution.

$ docker volume create ftm2
$ docker run --rm -v ftm2:/root/.m2 -v "$PWD/subjects/jsoniter":/w -w /w \
    maven:3.9-eclipse-temurin-8 mvn -B -DskipTests test-compile
[INFO] BUILD SUCCESS

JDK 8 is not a convenience choice. fastjson declares <jdk.version>1.5</jdk.version> and jsoniter <source>1.6</source>; javac dropped 1.5 after JDK 11 and 1.6 after JDK 12, so any modern JDK refuses both outright.

Dataset provenance matters because IDoFT is a living catalogue — rows and statuses change over time, so an unpinned clone would not reproduce the same case pool.

03

Case selection

Selection began from IDoFT's 8,075-row catalogue and narrowed by declared rules rather than convenience.

# 1. OD / OD-Vic rows with a usable status -> 1,438 rows
$ python3 -c "..." # proper CSV parse, not awk -F,
rows written: 1438

# 2. rank projects by OD density
$ awk -F, '{print $1}' manifest/pool_raw.csv | sort | uniq -c | sort -rn | head -25
Why a CSV parser, not awk

Test names in this file contain commas inside quoted fields. Splitting on -F, shifts columns and produces phantom categories such as []) and with existent item. A real parser also guarantees no legitimate OD row is silently dropped.

The top-25 projects were filtered against the declared rejection rules (no Android, Spring, web frameworks, databases, Kafka, Docker, Hadoop, Spark, Flink, Cassandra; no integration-test/e2e/benchmark modules; prefer small pure-Java libraries). Four survived; two were selected: json-iterator/java and alibaba/fastjson, both single-module JSON libraries.

Eight victims were drawn, 4 + 4, each in a distinct test class. One initially chosen fastjson victim was replaced after cross-referencing fixing PRs:

Why one case was swapped before any run

DateTest5_iso8601.test_date and DateTest.test_date were both fixed by fastjson PR 2148 — one PR, one root cause. Keeping both would have spent two of four slots on the same underlying defect. It was replaced by MaxBufSizeTest.test_max_buf, giving four distinct fixing PRs (2148, 3291, 2291, 2133) and therefore four independent root causes.

04

Harness architecture

Five components in src/. Each design decision below was forced by a property of the subjects, not chosen for elegance.

  1. runner/FtRunner.java — order executor

    Executes a declared sequence of test methods in one JVM, in order, emitting one machine-readable line per test with status, exception, message and stack frames.

    Two decisions that determine validity

    One fresh JVM per order. Static state is the phenomenon under study; if orders shared a JVM, pollution would leak between experiments and every measurement would be meaningless. One container per batch keeps this affordable — a container per order would make a 722-candidate scan unusable.

    Driven through JUnit 4's Request.method(). Both subjects are JUnit 3 (2,132 of fastjson's classes extend TestCase; jsoniter has zero @Test annotations). Request.method() routes JUnit 3 classes through JUnit38ClassRunner, so one code path covers both styles.

  2. runner/FtList.java — candidate enumeration

    Implements the frozen definition literally: a public, no-arg, void method named test* on a non-abstract public TestCase subclass. Classes are loaded with Class.forName(name, false, loader) so no subject static initialiser runs during enumeration.

    $ java -cp "$CP" FtList /w/target/test-classes
    jsoniter TOTAL 383
    fastjson TOTAL 4445

  3. extract_static.py — resource extractor

    The hypothesis under test. Disassembles bytecode and records every getstatic / putstatic as owner.field:descriptor with its bytecode offset. Attribution per test method covers the method itself plus setUp, tearDown and <clinit>, then N hops into project-owned callees.

    $ javap -p -c -cp "$CP" com.alibaba.json.bvt.parser.DateParserTest
    5: putstatic #5 // Field com/alibaba/fastjson/JSON.defaultTimeZone:Ljava/util/TimeZone;
    Why javap instead of ASM

    Zero external dependencies, and javap -c already resolves the constant pool into exactly the frozen identifier format — owner, field, descriptor — with the bytecode offset attached. That satisfies the evidence-integrity gate ("every overlap names the exact field and bytecode location") without extra machinery.

    One parsing defect was found and fixed: javap omits the owner for fields declared in the class being disassembled, printing bare DEFAULT_GENERATE_FEATURE:I. Left unqualified, identically-named fields in different classes collapse into one phantom shared resource. They are now qualified with the declaring class.

  4. step_scan.py — exhaustive single scan

    For each case, runs [candidate, victim] for every candidate and records the victim's outcome and normalised failure signature. Per the frozen single-scan protocol this executes once; every strategy is later replayed offline against this one table, so no strategy can trigger extra executions and inflate its own apparent cost advantage.

  5. step_analyze.py / step_replay.py — offline evaluation

    OBO, five seeded random orders and the resource ranking are replayed against the stored outcome table; accepted pairs then get 10 clean replays with Wilson 95% intervals. A replay counts only when the normalised signature matches — a timeout, compile error or OOM is never scored as the same reproduction.

A classification that was not in the plan

Hour 2 was expected to confirm every target passes alone. Two did not. FJ-01 and FJ-02 fail alone 10/10 and pass after a predecessor — they are brittle tests needing a state-setter, not victims needing a polluter. The protocol was generalised to both directions: an OD-relevant candidate is one that flips the target away from its isolation behaviour.

06

Two validity corrections

Both were caught by checking results that looked too good, and both would have produced a confidently wrong report.

6.1  jsoniter's suite execution context

The first scan reported 182 of 210 candidates as polluters of JI-01 — an apparently excellent result. Every one carried the identical exception:

com.jsoniter.spi.JsonException: javassist.CannotCompileException:
  by java.lang.LinkageError: attempt to duplicate class definition

An identical signature across 182 supposedly independent polluters is not order dependence; it is one systematic fault. Inspecting the build configuration revealed the cause:

$ grep -A15 surefire subjects/jsoniter/pom.xml
<reuseForks>false</reuseForks> <forkCount>4</forkCount>
<include>com.jsoniter.suite.StreamingTests</include>
<include>com.jsoniter.suite.NonStreamingTests</include> ...

jsoniter never runs test classes directly. Surefire runs five suite classes, each in a fresh JVM, and each suite's @BeforeClass selects the runtime codegen mode (JsonIterator.enableStreamingSupport()). Running raw test methods without that context left jsoniter's javassist codegen to define the same generated class twice.

The fix and its effect

FtRunner gained a -s <SuiteClass> flag that invokes the declared suite's @BeforeClass before every order, reproducing the project's real execution context. The false polluters went from 182 to 0. A widened scan across the full module (382 candidates) also returned 0, confirming the zero is real rather than a new artifact.

6.2  The environment "fix" that erased the phenomenon

FJ-01 and FJ-02 failed alone under the container's UTC default, by exactly eight hours. The apparent fix was to set TZ=Asia/Shanghai, and it worked — both then passed 10/10 in isolation.

That fix was wrong. These tests fail alone because they require JSON.defaultTimeZone to have been set by a predecessor. DateFieldTest8.setUp writes it globally and never restores it:

protected void setUp() throws Exception {
    JSON.defaultTimeZone = TimeZone.getTimeZone("Asia/Shanghai");
    JSON.defaultLocale = Locale.CHINA;
} // no tearDown restores either field
Why this matters more than the bug itself

Forcing the timezone made the state-setter's write a no-op, deleting the exact order-dependence under measurement. The override was removed and OD direction is now derived empirically from isolation behaviour. The durable rule: "target fails alone" is a classification, never an environment defect to be fixed.

# the decisive check, run with no TZ override
victim alone (UTC) -> FAIL
[DateFieldTest8#test_0, victim] -> PASS

08

Why the results came out this way

8.1  The overlap signal scored zero everywhere

|writes(candidate) ∩ reads(victim)| was 0 for every candidate in every case. The ranking therefore fell back entirely to tie-breaking by declared order, making the resource strategy byte-identical to OBO and the saving exactly 0%.

This is not a weak signal. It is no signal, and the cause is call depth, not a flaw in the principle. Traced concretely on FJ-02:

DateParserTest.setUp@5      --PUTSTATIC-->  JSON.defaultTimeZone
JSON.defaultTimeZone      --GETSTATIC-->  TypeUtils.cast@536

The target calls JSON.parseObject(...). The read of defaultTimeZone happens inside TypeUtils.cast, which is two hops below the test method. The frozen scope permits one hop, so the extractor sees the write but never the matching read — and an intersection needs both sides.

8.2  What the depth ablation shows

At depth 2 the FJ-02 state-setter is ranked first of 722 instead of 39th — the effect the project claims, demonstrated. But the other three cases do not move at all, so the median saving stays 0% and the gate still fails. Depth 3 adds nothing beyond depth 2.

The precise conclusion

Deepening the resource scope is necessary but not sufficient. Where a static field genuinely mediates the interference and lies within reach, the signal is decisive. Where the interference travels through paths this model does not represent, more depth changes nothing.

8.3  Why jsoniter produced nothing

After the suite-context fix, no single predecessor reproduced any jsoniter failure — not within the declared package scope (210 candidates), and not across the full module (382). The IDoFT labels were derived from whole-suite reordering, where a failure may require several predecessors or a suite-level state accumulation. The frozen pairwise [c, v] model cannot express that, so these are true negatives of the model, not evidence that the labels are wrong.

8.4  Why random beat both baselines on three cases

Random ordering is not smarter; it is unbiased. FJ-03 has 6 relevant candidates among 524, and OBO's alphabetical ordering happens to place them late (rank 368). A shuffle has no such systematic bias, so its expected position is roughly uniform. This is a genuine caution for the project: OBO is a weak baseline on alphabetically-clustered suites, and any future claim must beat random, not only OBO.

Decision: NARROW

Not Go — three of five gates fail and the headline mechanism returned a null result at its frozen scope. Not Pivot — the product contract held: the containerised runner, failure-signature equivalence, deletion checks and statistical replay all worked, and where the signal could see the resource it delivered a 97.4% saving. What is refuted is the resource scope, not the approach.

Scope changes carried into the proposal:

  • Redefine resource scope as transitive intra-project reachability at a declared depth (≥2), reporting depth and its cost; hop-1 survives only as an ablation.
  • Classify OD direction (victim / brittle) before search; forbid environment changes that alter isolation behaviour without recorded justification.
  • Require execution-context fidelity as a build-gate artefact, proven against an uninstrumented baseline; treat harness-induced outcomes as a first-class failure mode.
  • Add order-history evidence as a ranked component.
  • Benchmark against random, not only OBO.
10

Threats to validity

  • n = 4 reproduced cases, both subjects JSON libraries. No claim generalises to Java projects at large.
  • One protocol deviation. definitions.md was frozen before the run, then amended to require execution-context fidelity after the jsoniter artifact was found. The alternative was knowingly reporting fabricated polluters. This is disclosed rather than hidden, and is the item most likely to be probed.
  • The package restriction can hide polluters. Both modules exceed 300 test methods, so the frozen rule restricts candidates to the victim's package. For FJ-02 that still leaves 722 candidates, so the rule fires without making the search tractable.
  • OBO is implemented as declared (alphabetical) order, a proxy for Surefire's filesystem order. Section 8.4 shows this proxy is itself a weak baseline.
  • Static analysis only. Reflection, filesystem, system properties, network and database state are out of scope and recorded as UNSUPPORTED — never as zero-overlap.
