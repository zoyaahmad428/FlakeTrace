# Design spec — FlakeTrace web UI over the runner CLI

**Date:** 2026-10-14 · **Status:** `APPROVED` by M2 on 2026-10-14 · **Owner:** M2 (Abdul Raffay)
**When:** Iteration 2 (after the Mid evaluation on 16 October 2026). Not part of the Mid demo, which
stays the terminal run in [[08-MidEval/demo-plan]], and not part of tag `mid-eval-v1`.
**Decision record:** [[03-Design/decisions/ADR-009-ui-over-cli]] (proposed).
**Agreed in a brainstorming session on 2026-10-14** (approach, labels, scope and tests below were each
approved by M2).

## 1. Goal

Show what FlakeTrace really does through the proposal-stage web UI (`POC/POC/flaketrace-ui`), so a
viewer can run a diagnosis and read its result screen by screen.

Success means:

1. Every value on screen comes from a real report produced by `py -m runner diagnose`.
2. Every part of the POC UI that FlakeTrace has not built is still visible, greyed out and labelled
   with the plan it belongs to, or with "not in current plan".
3. Nothing simulated or recorded from the POC is shown.

## 2. Decisions taken

| Question | Decision |
| --- | --- |
| Live or recorded? | **Both.** *Live*: the UI runs the real CLI (about 20–40 s per case, measured: F1 23.3 s and 37.0 s in [[evidence-m2]]). *Open report*: the UI loads an existing report JSON, e.g. the seven in `eval/reports/`; this is also the fallback when a live run fails |
| How does the browser reach the tool? | A new small Python backend that **runs the CLI as a subprocess** — not the POC backend, not Node |
| Unbuilt POC parts | Kept and greyed: **"NOT BUILT YET — PLANNED FOR X"** with X taken from a written source; **"NOT BUILT — NOT IN CURRENT PLAN"** where no source plans it |
| POC simulated data | Deleted: `src/lib/sim.ts`, `src/data/recorded.json`, and `flakyReproduces` in `src/screens/Certificate.tsx` (`(i * 7 + 3) % 20 < 13`) |
| Owner | M2, including the backend and everything connecting the UI to the tool |

**Main constraint (why the UI calls the CLI):** the UI must never show something the tool did not
produce. Calling the CLI — the same command as the terminal demo — and reading only the report file it
writes makes that true by construction, and lets `runner/` change without breaking the UI.

## 3. Layout

New top-level folder, owned by M2. `POC/` is not changed (root `CLAUDE.md`: legacy, read-only).

```
ui/
  server.py            backend: Python standard library http.server on 127.0.0.1:8765
  tests/               unittest; fakes here only, named Fake…
  web/                 React + Vite + TypeScript, copied from POC/POC/flaketrace-ui
    src/lib/report.ts  the only mapping from report JSON to what each screen shows
  start.cmd            starts the backend and the web app (Windows cmd)
  README.md
```

The web app runs on port 5174 and forwards `/api` to 8765, as the POC does (`vite.config.ts`).

## 4. Backend API

| Endpoint | Behaviour |
| --- | --- |
| `GET /api/health` | Which of `java`, `javac`, `javap`, `mvn` are on PATH, and the Python version |
| `POST /api/diagnose` `{project, victim, n?, order?}` | Starts `py -m runner diagnose --project … --victim … [--n …] [--order …] --records <new temp folder for this job>` and returns `{job_id}` at once |
| `GET /api/jobs/<id>` | `running` (with start time and the exact command); `done` with the report JSON and its file path; or `failed` with the CLI's message and the last lines of its output |
| `GET /api/reports` | Names of the reports in `eval/reports/` |
| `GET /api/reports/<name>` | One of those reports |

Job result from the CLI exit code (`runner/cli.py`):

| Exit | Meaning in the CLI | Job state |
| --- | --- | --- |
| 0 | Report written as `*.report.json` in the records folder | `done` — the backend reads that file |
| 1 | A tool failed: Maven, a timeout, or resource evidence | `failed` — "Diagnosis could not run" + message |
| 2 | Bad input: no `pom.xml`, victim not `Class#method`, bad order file, negative shuffles | `failed` — input error, shown on the Target screen |
| 3 | "No report: <status>" | `failed` — "Runner finished with status X; no report can be built for this status" + record path |

Rules:

1. **One job at a time.** A second `POST /api/diagnose` while one runs returns `busy`; two runs would
   share the project's `target/` folder.
2. **No invented results.** Data comes only from the report file. A missing or schema-invalid report
   after exit 0 makes the job `failed`.
3. **Every report is validated** against `eval/schema/report.schema.json` before it is returned, both
   live and from `eval/reports/`.
4. **Local only:** the server binds `127.0.0.1`.
5. **Timeout:** a job is killed after 10 minutes and reported `failed: timed out`. The runner keeps its
   own 120 s per-JVM timeout.
6. **Records** go to a new folder under the system temp directory per job — never inside the
   repository or the analysed project. The runner's source-integrity check still applies.

## 6. States in live mode

| State | Cause | Shown |
| --- | --- | --- |
| Tools missing | `/api/health` lacks a tool | Diagnose disabled, naming the missing tool; open-report mode still works |
| Bad input | Exit 2 | The CLI message under the field |
| Busy | A job is running | "A diagnosis is already running (started HH:MM)" |
| Running | Job started | "Running real JVM tests…", elapsed seconds, the exact command |
| Tool failed | Exit 1 or timeout | "Diagnosis could not run", the message and last output lines |
| No report | Exit 3 | The status and the record path |
| Done | Exit 0 and a valid report | Screens filled; the report file path shown |
| Backend down | `/api` unreachable | "Backend not running — start `ui\start.cmd`"; a local report file can still be opened |

## 7. Tests

Each test is seen failing before the code that makes it pass. Fakes live under `ui/tests/` only and are
named `Fake…`; production code never imports them.

**Backend (`ui/tests/`, unittest):**

1. Exit codes 0–3 map to the job states in section 4, using `FakeCli` (a script that exits with a chosen
   code and writes or omits a report).
2. Exit 0 with no report, or with an invalid report, gives `failed`.
3. A second diagnose while one runs gives `busy`.
4. A job over the limit (set to 1 s in the test) is killed and reported `failed: timed out`.
5. The server binds `127.0.0.1`.
6. `/api/reports` lists exactly the seven files in `eval/reports/`, all schema-valid.
7. One real run: `POST /api/diagnose` on F1 (`odfixture.ConfigVictimTest#expectsDefaultMode`) ends
   `done`, `VERIFIED`, polluter `ConfigPolluterTest#pollute`. Skipped when JDK or Maven is missing, as
   the `runner` tests are.

**Frontend (`ui/web/`, Vitest):**

1. `report.ts` maps each of the seven reports to the values in the table in section 5.
2. Every `null` field becomes a stated reason.
3. Each greyed part shows exactly the label in section 5.
4. The built app contains no `sim.ts`, no `recorded.json` and no `flakyReproduces`.
5. `tsc` and `vite build` pass.

**CI:** a new `ui` job in `.github/workflows/ci.yml` runs both. Whether it becomes a required check in
branch protection is a team decision, because it changes the rule M1 and M3 merge under.

**Manual check:** start `ui\start.cmd`, run F1 live, open N1's report; record the real result in
[[evidence-m2]].

## 9. Delivery

Each step is one pull request that M2 commits after reading the diff and another member approves.

1. This spec, ADR-009 and the ownership records.
2. Backend and its tests; the `ui` CI job.
3. POC UI copied to `ui/web/` with the simulated data removed, and the no-simulated-data test.
4. `report.ts`, open-report mode and the screen labels, with tests on the seven reports.
5. Live mode: Diagnose, job polling and the states in section 6.
6. Manual end-to-end check, evidence and the demo-plan update.

## 10. Out of scope

- Progress lights for each diagnosis stage (the runner would have to report progress; a later spec).
- Several jobs at once, user accounts, hosting the UI online.
- Any analysis the CLI does not already do.
